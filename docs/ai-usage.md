# AI 编程助手使用说明

> 这是交付物之一，也是答辩素材。**从 SDD 阶段起就开始如实记录**，不要事后补写、不要美化。

## 1. 工具与分工

| 环节 | 工具 | 我做什么 | AI 做什么 |
|---|---|---|---|
| 需求分析与可行性评估 | Claude | 提出问题、做取舍 | 拆解需求、指出风险（如号码来源矛盾） |
| 规格（SDD）起草 | Claude | **评审、裁剪、拍板待决问题** | 起草 `specs/` 全部文件与 AC |
| 编码与测试 | Codex / Claude Code（待填） | 逐任务审查、纠错、验收 | 按 `tasks.md` 一次一个任务：先测后码 |
| 文档 | AI 辅助 | 核对事实、补充亲身理解 | 起草 README / 合规说明 |

## 2. 工作方式（SDD 循环）

`规格 → 任务 → 先写测试(带 AC 编号) → 实现 → 全量测试 + ruff → 人工审查 → 提交`

关键约束：
- 项目根的 `AGENTS.md` 规定了红线、工作流与"遇到歧义先停下提问"。
- 每个测试函数名带 AC 编号，`scripts/ac_coverage.py` 生成「AC → 测试」对照表（`docs/ac-coverage.md`）。
- 一次只给 AI 一个任务（≤ 约 3 小时），上下文 = `AGENTS.md` + 该任务相关的 spec，避免漂移。

## 4. AI 犯过的典型错误（持续追加）

> 例：「AI 把 `datetime.now()` 写进了业务代码，违反时钟注入 → 我要求改为 `Clock` 并加了静态扫描测试」。
> 这一节最能体现"我是在驾驭 AI，而不是被 AI 驾驭"。

- AI 用正则做号码掩码时两次误伤正常文本：T-02 把 ISO 时间戳（`2026-11-14T09:00:00Z`）当成号码，T-04 审查又发现 32 位十六进制请求 ID 会被掩码（实测约 13% 的随机 ID 受影响，日志与响应头对不上）。两次都是人类审查发现 → 改为跳过日期前缀，并识别、保留 hex/UUID 令牌，各补一条回归测试。
- AI 默认接受 Pydantic 的宽松转换，`weight: true` 变成 `1`、`"30"` 变成 `30`、`enabled: "false"` 变成 `False`，与"类型错误应 422"的意图不符 → 审查后配置 schema 改用 `StrictInt`/`StrictBool`。
- AI 在 T-04 把"库为空时自动播种"写成已知缺口而不是先记入 `CHANGELOG` 待决 → 审查后按 spec 原文补上 `SEED_DEFAULTS=true` 的启动播种与测试。
- AI 的日期豁免按"token 起点像日期"整段放行，`2026-11-14 555-555-0101` 中的完整号码实测漏网；异常堆栈也绕过了当时的消息级过滤器。两处都直到统一遗留问题评审才被发现 → 日期改为独立分支并前置，脱敏下沉到 Formatter 层，补日期+号码、traceback 两组回归测试。
- T-07 写 POOL-005 测试时把二次重算的候选数算错：忘记首次评分已自动入池的 20 条不会再次进入候选，断言 42 而实际是 22；测试先失败后修正。说明写断言前要显式列出集合的组成。
- T-12 第一次跑闸门测试即报 `'ItemEntry' object has no attribute 'phone_hash'`：处理器组事实时需要明细的号码快照，而 T-11 的读模型只暴露了 `phone_masked`。补上 `phone_hash` 字段（API 响应仍不含它）。说明读模型要覆盖下游消费者的全部输入，而不是只覆盖当前 API 的展示字段。
- T-13 引入自动完成后，T-12 的 CAMP-005 测试「全部发完后再 start」由 200 变成 409 而失败：任务已完成，重复 start 本应非法。测试改为断言 409，保留「唯一消息数不增加」的核心断言。说明跨越任务的行为变化要回看旧测试的语义，而不是只让新测试通过。
- T-14 的 `/demo/reset` 直接把 `Base.metadata.drop_all` 与 `create_schema` 写进 API 路由，被架构守卫抓到 `api → models` 越层；改为 `api → DemoService → schema_repo → models`。功能测试全绿时守卫测试才是唯一报警者——说明「能跑通」不等于「分层正确」。
- T-15 的熔断恢复测试第一版只把 `FakeClock` 推进 2 秒，忽略了种子里的 `GLOBAL 5/10s` 频控：刚失败过的 5 条重试立刻又被整体延迟，任务停在 `RUNNING`。改为推进 11 秒。说明测试一个机制时，要同时考虑同一条链路上其它闸门的相互作用。

- T-18 计划用应用内 Browser 预览做冒烟，但预览器的 `bash` 在 Windows 上以 WSL 路径执行（`/bin/bash` 不存在），且 Browser 预览本身未启用，浪费了一轮配置。说明先确认环境能力，再决定验证方式；最终退回到 TestClient 静态断言 + `node --check` + 手动清单。
- UI 视觉改版时才发现 `.hidden` 会被后定义的 `.error-bar { display: flex }` 覆盖，错误条其实一直显示——因为初版 UI 从未在真实浏览器里打开过，静态测试也覆盖不到。说明「测试全绿」不等于界面可用；UI 交付前至少要人工打开一次，样式类名冲突应优先用组件级选择器或 `!important` 兜底（本次改为后者）。
- T-20 的 E2E-1 第一版建 Worker 时没启用回执轮询，跑出 success=6 / failed=2，而 05 §3 是 5/3：漏了 9005 的失败回执只有在回执被应用后才会把那条 SENT 改成 `FAILED(DELIVERY_FAILED)`。改为 `receipts=True` 并在完成后推进时钟再 tick 一次。说明 e2e 的期望数字包含回执阶段的状态变化，不能只跑到 `COMPLETED` 就断言。
- T-20 的 E2E-7 第一版直接重试，结果 9004 停在 `RETRY_WAIT`：种子里的 `GLOBAL 5/10s` 在前一次 tick 已用满 5 次调用，重试被频控闸门整体推迟。场景测试要只验证一个机制时，先把干扰的规则放宽；这与 T-15 的教训同源（同链路其它闸门会介入）。
- T-20 的 E2E-9 在窗口滑动后把时钟精确推进 600 秒，明细仍被延迟：频控窗口用的是 `created_at >= now - window`（含边界），最早的发送正好落在边界上又被计入。改为推进 601 秒。说明涉及开闭区间时不要假设"刚好等于"就会放行。
- 在 Windows 上直接跑 `pytest` 时，既有的 `.pytest_basetemp` 目录被占用会报 `PermissionError`；本次改用每个任务独立的 `--basetemp=.pytest_basetemp_tXX`，避免与旧进程的临时目录冲突。
