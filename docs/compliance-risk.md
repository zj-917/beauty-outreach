# 合规与风险控制说明

> 交付物 6（对应 `specs/00-constitution.md` R-11：**文档诚实**）。
> 本文如实区分「原型实际做法」与「生产环境要求」，并列出本原型的已知边界。
> 平台政策会变化：本文的平台表述来自项目设计假设（`specs/01-overview.md` §3 A-1~A-5），**本环境无法访问 Meta 官方文档做线上核对**，正式对接前必须逐条对照官方文档确认。

## 1. 适用范围

本仓库是一个**本地原型**：不访问真实 Instagram / WhatsApp / Meta 网络，不抓取、不模拟登录、不购买或使用第三方号码。默认 Provider 为 `MockMessenger`；`WhatsAppCloudStub` 永远返回 `501 PROVIDER_NOT_ENABLED`；测试夹具拦截一切对外连接（`tests/conftest.py` 的 `no_network`，含 `connect` / `connect_ex` / `sendto` / `getaddrinfo`）。

## 2. 关键假设（必须先接受，才谈得上合规）

| 编号 | 假设 | 说明 |
|---|---|---|
| A-1 | 号码来源 | Instagram 公开资料不含手机号；原型约定号码只来自**企业自有授权数据 / 用户主动留资**，随线索行携带 `phone` 与 `consent`。原型无法验证号码归属与授权的真实性。 |
| A-2 | 线索来源 | 官方接口不提供「按关键词搜索任意公开用户」，题目亦禁止爬虫 → 只用 Mock 数据与 CSV/JSON 导入；`InstagramApiStub` 仅为接口形态示意。 |
| A-3 | 发送通道 | 真实 WhatsApp 发送需要企业认证、已审核模板，并遵循 opt-in 与退订要求 → 原型只用 `MockMessenger`；真实实现仅为 Stub。 |
| A-4 | 退订语义 | 退订即永久拦截，不提供重新订阅流程（更保守）。 |
| A-5 | 管理端 | 单一管理员、静态 token 鉴权，不做账号体系。 |

## 3. 红线与实现证据

| 红线 | 原型做法 | 证据 |
|---|---|---|
| R-1 数据来源合法 | 只有 Mock / CSV / JSON 导入；Stub 不联网 | `app/providers/lead_source/*`；AC-LEAD-012 / SYS-006 |
| R-2 默认 Mock、测试禁网 | `MESSENGER_PROVIDER=mock`；网络守卫夹具 | `tests/conftest.py::no_network`；AC-SYS-006 |
| R-3 无授权不触达 | 闸门 4（CONSENT）无记录 / 已撤销即跳过 | AC-COMP-002/003、CAMP-011 |
| R-4 退订 / 黑名单绝对优先 | 闸门 2（SUPPRESSION）先于其它；无 force / bypass 参数 | AC-COMP-005、CAMP-010；全仓无 `force` 类开关 |
| R-5 退订可达且即时 | 每条消息追加中英退订页脚；入站 STOP 同事务写 suppression + 撤销授权；闸门每条的实时查库、不缓存 | AC-TPL-005、COMP-006/007/008 |
| R-6 不重复发送 | 幂等键 sha256(task:lead:template) + 全局唯一约束 + 同键重发 + 跨任务同模板防重 | AC-CAMP-003/005/009/014、E2E-3/4 |

| R-9 审计不可篡改 | `audit_log` 只追加（SQLite 触发器），与业务同事务；SHA-256 哈希链可校验 | AC-AUD-001~005 |
| R-10 筛选可解释、人工可覆盖 | 每条评分写 `score_reasons` / `top_keyword`；人工决定不被重新评分覆盖 | AC-SCR-009/012、POOL-003 |
| R-11 文档诚实 | 本文与 README 明确 Mock 与生产的差异 | 本文 |

## 4. 原型 vs 真实平台（差异清单）

| 方面 | 原型（本仓库） | 真实 WhatsApp / Instagram |
|---|---|---|
| 线索获取 | Mock 数据集、CSV/JSON 导入；号码与授权随行录入 | 官方接口不提供任意用户搜索；号码需通过合法 opt-in 渠道获取 |
| 发送 | `MockMessenger` 按手机尾号确定性模拟受理 / 失败 / 限流；内存回执 | 需要企业账号、模板审核、消息额度与质量评级；接口有速率限制 |
| 幂等 | Provider 按幂等键返回同一 `provider_message_id` | 真实接口通常**不接受客户端幂等键**；崩溃重发可能产生重复消息（见 §5 R-6） |
| 回执 | 内存队列 + `poll_receipts()`；也支持签名 Webhook | 以 Webhook 回调为准，需校验签名、处理重放与乱序 |
| 退订 | 原型语义：STOP 即永久 suppression + 撤销 consent | 平台另有退订 / 拉黑机制与合规要求，二者需同步 |
| 频控 | 基于 `send_log` 的滑动窗口计数 | 平台级速率限制与业务自控并存；多 Worker 需令牌桶 |
| 授权凭证 | `source` + `evidence_ref` 文本，无外部验证 | 生产需可追溯的 opt-in 记录（时间、渠道、原文、撤回方式） |

## 5. 风险清单

| 编号 | 风险 | 影响 | 原型现状 | 生产要求 |
|---|---|---|---|---|
| CR-1 | 号码归属与授权真实性无法验证（A-1） | 触达未授权用户，直接违反 R-3 | 导入即信任 `consent` 字段 | 接入自有留资系统 / 双重确认；抽样复核；保留 opt-in 原文 |
| CR-2 | 用户资料文本（`bio` / `display_name`）可能自带号码 | 与「完整号码不得出现在 API / UI」的意图冲突 | 原型按用户公开内容原样返回，不额外脱敏（Mock 数据不含号码） | 导入与展示前扫描并脱敏；或产品层面禁止展示原始简介 |
| CR-3 | 退订永久不可撤销（A-4） | 误判 STOP 后无法恢复沟通 | 保守实现 | 提供人工申诉 / 重新授权流程，并保证新授权可覆盖旧 suppression |
| CR-4 | 静态 token、无账号体系（A-5） | token 泄露 = 全量管理权限 | 仅 `sessionStorage` 保存，恒 HMAC 比较 | SSO / RBAC / 短时令牌 / 操作人审计 / IP 限制 |
| CR-5 | 单进程 SQLite + 单 Worker | 吞吐有限；多实例部署会破坏频控与审计链假设 | 原型单进程 | Postgres + 多 Worker + `SKIP LOCKED`；频控改 Redis 令牌桶 |
| CR-6 | 真实 Provider 无幂等键 | 崩溃后同键重发可能造成重复消息 | Mock 幂等掩盖了该风险 | 发送前持久化 intent、以 provider message id 对账、接受并监控极小重复窗口 |
| CR-7 | 密钥与密文管理 | 环境变量泄露 / 无法轮换 | `.env` 开发密钥 | KMS / 密钥轮换 / 密文重加密迁移；最小权限 |
| CR-8 | 消息正文落库（`task_item.rendered_body`） | 数据库泄露会暴露内容 | 为同内容重试而保存 | 加密存储 / 发送成功后清理 / 访问审计 |
| CR-9 | 回执丢失 | 状态停在 SENT，统计偏低 | Mock 内存队列重启即丢 | 以签名 Webhook 为准，回调重放与对账任务 |
| CR-10 | 无自动数据保留与删除 | 长期留存超出必要范围 | 原型不清理 | 保留期、自动清理、导出与删除请求（DSAR）流程 |
| CR-11 | 平台政策变化 / 表述不准确 | 合规文档失真 | 本文基于项目假设，未在线核对 | 上线前逐条核对 Meta 官方文档；政策变更纳入评审 |
| CR-12 | 多语言 / 地区法规差异 | 不同市场对营销消息要求不同 | 原型无地区化合规逻辑 | 按地区配置静默时段、退订文案与频控上限 |

## 6. 生产化清单（从原型到可用系统）

1. **平台接入**：企业认证、号码与模板审核、消息额度与质量评级；对照官方文档确认 opt-in、退订与模板规范（CR-11）。
2. **授权与来源**：可追溯的 opt-in 记录（渠道、时间、原文、撤回）；号码归属校验；导入前合规扫描（含 CR-2 的文本脱敏）。
3. **发送可靠性**：真实 Provider 的幂等或发送前后对账（CR-6）；Webhook 签名校验 + 重放保护；回执对账与补偿。
4. **频控与伸缩**：Postgres + 多 Worker（`SKIP LOCKED`）；Redis 令牌桶；全局 / 单收件人 / 平台级限制叠加。
5. **安全**：SSO / RBAC、操作人追踪、短时令牌、KMS 与密钥轮换、数据库加密、审计日志异地留存。
6. **数据治理**：保留期与自动清理、DSAR、访问日志、最小化字段；消息正文加密与清理（CR-8）。
7. **运营**：静默时段按地区配置、退订申诉流程、内容审核、投放监控与熔断演练。
8. **观测与应急**：指标（发送成功率、失败原因、频控延迟、熔断）；告警；事故响应与暂停开关（pause / cancel）。

## 7. 已实现的验证证据

- **泄漏扫描**（E2E-5）：对 API 响应、日志、`audit_log`、`send_log`、`task_item.last_error_message` 与 SQLite 文件字节（含 `-wal` / `-shm`）逐一断言无完整号码。
- **脱敏单元测试**：`mask_phone` 参数化用例；日志过滤器覆盖号码、token、签名头与 traceback。
- **审计**：只追加触发器、同事务回滚、哈希链校验、API 查询脱敏。
- **网络隔离**：`no_network` 自动夹具 + 故意连外网被拦截的测试；Stub 调用即 501。
- **AC 覆盖**：`docs/ac-coverage.md`（`python scripts/ac_coverage.py`），未覆盖 P0 = 0。

## 8. 明确不做（避免误解）

- 不实现真实 Instagram 采集、真实 WhatsApp 发送、爬虫、模拟登录、账号体系、多租户、数据库迁移。
- 不提供绕过授权 / 黑名单 / 频控的任何开关；退订不可恢复。
- 不采集 `specs` 之外的字段；不做第三方统计或广告追踪。
